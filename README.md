# TrentoProjects
# Radar Hand-Gesture Recognition -- MSP430FR5994 + BGT60LTR11AIP

Radar-based hand gesture recognition, ported from an MSP432/CMSIS-DSP
thesis project onto the 16-bit MSP430FR5994 (no FPU). Pipeline:

```
BGT60LTR11AIP (IFI/IFQ analog out)
        |
   ADC12_B, hardware-triggered @ 4 kHz  (radar_configuration.c)
        |
   ring buffer (I_queue / Q_queue)
        |
   on-chip STFT: window -> complex FFT (LEA) -> log2 magnitude  (STFT.c)
        |
   DMA -> UART @ 115200 baud, 0xC0-marked spectrogram columns  (main.c)
        |
   host PC: log / visualize / build a training dataset
```

Firmware does the STFT on-chip. Nothing on the PC side recomputes it --
every Python tool here either just displays what's already computed, or
diagnoses the transport (serial link) between the board and the PC.

---

## Wire format

Everything the firmware sends is prefixed `0xAA 0x55`, then a 1-byte
marker telling you what follows:

| Marker | Meaning                  | Body size | Sent               |
|--------|---------------------------|-----------|---------------------|
| `0xC0` | Spectrogram column         | 256 bytes (`int8_t[256]`) | every hop (~31 Hz) |
| `0xC2` | ADC sample-rate snapshot    | 2 bytes (`uint16_t`)      | 1 Hz |
| `0xC3` | STFT/DMA timing profile     | 6 bytes (3x `uint16_t`)   | 1 Hz |

All three frame types share one UART stream. Every tool below has to know
about all three markers to stay byte-aligned, even the ones that only
care about one of them -- if a script skips a marker it doesn't
recognize, it desyncs on the next frame.

## Firmware files

| File | Purpose |
|---|---|
| `main.c` | Main loop + all ISRs (ADC trigger, ADC result, 1 Hz snapshot timer, DMA-done) |
| `radar_configuration.c/h` | Clock/GPIO/UART/ADC/Timer/DMA setup, low-level UART frame senders |
| `STFT.c/h` | On-chip windowing + complex FFT (LEA) + log-magnitude, produces each spectrogram column |
| `window_q15.c/h` | Precomputed Q15 Hanning window coefficients (generated by `window_q15_generator.py`) |

## Python tools

| File | What it's for | When to use it |
|---|---|---|
| **`radar_stft_capture.py`** | **Live spectrogram viewer.** Connect/Disconnect button, rolling waterfall plot, optional `--log-file` to record a session in the format the dataset tools below expect. | Day-to-day: watching gestures live, and recording capture sessions. |
| **`STFT_check.py`** | Text-mode frame inspector. Prints every frame with a timestamp, peak bin, and motion-peak bin; `--log-file` also logs columns; `--show-columns` dumps raw values. | Debugging: "is the board sending sane data right now?" without needing a plot window. |
| **`rate_check.py`** | Headless throughput check: counts columns received per second and inter-column gaps, no plotting. | Quick sanity check after any firmware change, or before a capture session -- confirms you're near 31.25 Hz with few/no resyncs. |
| **`test1_adc_rate.py`** | Watches only the 1 Hz `0xC2` ADC-fill-rate snapshots. Independent of the DMA/UART path (different timer/clock), so it isolates "is the ADC keeping up?" from "is the transmit path keeping up?" | Deeper throughput debugging -- narrowing down *which* stage of the pipeline is the bottleneck. |
| `visualizer.py` | Batch tool: turns a logged capture file into a literal grayscale PNG (min-max normalized). | Quick "does this file have real data in it?" check on a saved capture. |
| `spectrogram_view.py` | Batch tool: presentation-quality plot(s) of one or more capture files, with the DC line and motion-peak trace overlaid (same look as the live viewer). Accepts multiple files for a side-by-side grid. | Reviewing/presenting saved captures after the fact (this is what produced the annotated spectrogram images used in this chat). |
| `splitter.py` | Cuts one long capture file into `WINDOW_SIZE`-column (currently 15, matches `STFT_SEGMENTS`) random sub-windows, for building training examples. | Dataset prep, once you have raw captures logged. |
| `window_q15_generator.py` | One-off: generates the Q15 Hanning window array for `window_q15.c`. | Only if `FFT_SIZE` changes -- not part of the normal workflow. |

### Superseded / not part of the current workflow
`denene.py` and `Serial_Graph.py` parse the old raw 6-byte IFI/IFQ frame
format from before the firmware did on-chip STFT. They won't produce
anything meaningful against the current firmware. Kept in the repo for
reference; not documented further here.

## Typical workflow

1. **Flash the firmware**, plug in the LaunchPad. Note the known quirk:
   after flashing / replugging USB, you need to press the physical reset
   button once before it starts transmitting (eZ-FET behavior -- the CPU
   stays halted post-flash until a real reset pulse).

2. **Sanity-check throughput** before doing anything else:
   ```
   python rate_check.py --port COM7 --duration 5
   ```
   Expect ~31.25 Hz column rate and few/no resyncs. If resyncs are high,
   don't move on to dataset capture yet -- see the note printed by the
   script.

3. **Watch it live** while making gestures:
   ```
   python radar_stft_capture.py --port COM7
   ```
   Click Connect. Confirm the motion-peak trace responds to your hand the
   way you expect.

4. **Record a capture session**:
   ```
   python radar_stft_capture.py --port COM7 --log-file captures/session1.txt
   ```
   Each line in the log file is one spectrogram column: 256
   space-separated `int8_t` values.

5. **Review the capture**:
   ```
   python spectrogram_view.py captures/session1.txt
   ```

6. **Cut it into training windows**:
   ```
   python splitter.py captures/session1.txt 20 captures/gesture_swipe
   ```
   (20 random 15-column windows, written into `captures/gesture_swipe/`)

Repeat steps 3-6 per gesture class, with a consistent naming convention
for the output directories (e.g. `captures/<gesture_name>/`) so labels
are recoverable from the folder structure later.

## Known issues / things still worth investigating

- **I/Q image leakage**: spectrograms show a faint mirrored copy of every
  real motion arc on the opposite side of DC. This is gain/phase
  imbalance between the BGT60LTR11AIP's I and Q analog channels, not a
  firmware bug. Likely fine to leave for classification (consistent
  across the whole dataset), but a correction step could clean it up if
  needed later.
- **eZ-FET USB bridge is the real transport bottleneck**, not the on-chip
  UART baud rate. Bypassing it with an external USB-UART adapter
  (FTDI/CP210x) is the next throughput lever if you ever need it.
- **ADC values not exceeding ~1028**: flagged in an earlier session,
  still open -- worth a look before this becomes a source of clipped
  dynamic range in the dataset.
